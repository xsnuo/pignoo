  总体评价

  作为一个个人维护的轻量框架，工程质量是中上的：模块划分清晰、中英双语 JavaDoc 完整、值参数全部走 PreparedStatement（值层面无 SQL 注入）、用 MethodHandle + 经典反射兜底做了性能取舍、Spring 事务集成用
  DataSourceUtils + TransactionSynchronization 做得规范、EntityMapper / EntityProxyFactory / FunctionNameGetter 均已缓存。

  最初一轮 review 列出的问题已基本清完（见下「已完成」）。当前纯代码层无遗留待修项；剩下的是一个值得排期的重构、测试补充，以及几个属于设计取舍、建议靠文档提示的点。

  二、设计层面的「脚枪」（不算 bug，属设计取舍，建议在文档 / README 醒目提示，而非改代码）

  - removeAll()/mixAll()/replaceAll() 在没有 filter 时是整表操作：List 语义的自然结果，但少写一个 .filter() 就清表，威力很大。
  - setter 自动回写 = 每次 setter 一条 UPDATE，非事务模式下各自独立提交、多字段无原子性；改多个字段应优先 mixById/replaceById。（可用 PignooConfig.openSetterProxy=false 关闭代理回写。）
  - autodatabase 的 RADICALLY 模式会自动执行 DROP COLUMN（EntityScaner.java:210-211 + DatabaseChecker4MySql.java:174）→ 数据丢失风险。目前靠 BuildMode 分级 + 日志 warning 兜着，属启动期工具，但建议默认更保守。

  已决策不做：
  - SQL 拼接保持各方法内联完整（SELECT/FROM/WHERE/ORDER BY 摆在一起），不抽公共 builder/helper。作者明确取舍——到 SQL 落地层不应用封装隐藏细节，宁可少量重复也要保证单方法内一眼看全整条语句。（曾试抽 selectFrom/appendWhere 等，因降低可读性已撤销，不再建议。）
